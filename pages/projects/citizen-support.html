Citizen Support AI Assistant

An LLM-powered conversational AI prototype developed for a Bradford Council project brief. The system combined retrieval-augmented generation (RAG) with rule-based service routing to help residents find information and navigate local council services through a conversational interface.

01 / The Problem

Accessing local council services can require residents to navigate multiple webpages, forms and service categories. Finding relevant information can be challenging when someone does not know which council service handles their enquiry.

Our goal was to explore whether a task-oriented conversational assistant could provide a single place for residents to ask questions in natural language and receive relevant guidance or links to official services.

02 / My Approach

The team developed a modular architecture combining predefined service workflows with AI-based retrieval and response generation. This helped us handle both structured service requests and more general enquiries.

  • Requirements and conversation design: Investigated intent classification, entity extraction, dialogue state, context handling and fallback strategies to inform a task-oriented conversational workflow.
  • Knowledge base and semantic retrieval: Council FAQ and public service content was organised into chunks, embedded and stored for similarity-based retrieval using FAISS.
  • Hybrid service routing: Keyword rules and predefined triggers directed certain requests, such as postcode lookups, to structured workflows rather than the general RAG response path.
  • Retrieval-Augmented Generation: LangChain coordinated the retrieved context and response prompts, while an OpenAI LLM generated natural-language answers grounded in relevant council information.
  • Context management and evaluation: Explored multi-turn dialogue handling and tested how the system performed when queries were ambiguous, incomplete or phrased differently from predefined rules.

03 / Evaluation & Findings

We evaluated the prototype using 154 test queries representing different council-service enquiries and user scenarios. We considered several measures rather than relying solely on whether a response sounded convincing.

  • Routing accuracy: Did the question reach the correct service area?
  • Response quality: Was the answer relevant and factually appropriate?
  • URL relevance: Did the suggested links match the enquiry?
  • Suggestion relevance: Were the follow-up suggestions useful?

Results and Error Analysis

The final project report recorded 85% overall accuracy under its internal evaluation framework, meeting the project's target. This is a reported aggregate result, not an independently validated measure of real-world reliability.

The most important weakness was incorrect intent routing. The system could generate a fluent response while addressing the wrong council service. Queries with missing context or ambiguous wording were especially difficult for the rule-based routing layer.

Retrieval quality also depended on knowledge-base coverage, while limitations in conversation memory affected some multi-turn interactions. These findings showed that chatbot quality depends on the entire pipeline—not just the language model.

Key takeaway: A coherent response is not necessarily a correct response. Accurate routing, relevant retrieved context and reliable dialogue state are essential for a public-service assistant.

05 / Reflection & Limitations

This project helped me understand how LLM applications depend on multiple components working together, including service routing, retrieval, prompt construction, conversation state and evaluation. Integrating an LLM alone is not enough to build a reliable assistant.

The project also highlighted the limitations of keyword-driven intent detection, incomplete source coverage and inconsistent handling of ambiguous or multi-turn enquiries. Future work would include improved intent classification, clarification prompts, better context retention and more representative user testing.

As this system concerns public services, real deployment would require stronger evidence of correctness, data governance, security and accessibility safeguards. The prototype was not an official council service and was not validated for unsupervised public use.
